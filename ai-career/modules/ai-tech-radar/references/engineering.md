# 工程实践分析

先回答业务为何需要这套方案，再解释实现。读文章时围绕以下链条提取，不强求原文没有的信息：

| 内容 | 要抓住的问题 |
|---|---|
| 业务任务 | 服务谁，输入与输出是什么，错误会怎样影响用户？ |
| 真实约束 | 数据和工具可用性、延迟／成本、长程状态、人工介入、部署与权限有哪些约束？ |
| 方案与取舍 | 为什么用这种架构、数据流程或评价方式？作者比较或放弃了什么？ |
| 效果证据 | 指标、数据集／业务范围、基线和条件是什么？是作者报告还是本轮实测？ |
| 可迁移部分 | 哪个机制能用于学生已有项目，迁移需要什么条件？ |

没有写出的架构、内部流量、收入收益或失败原因保留未知。公开文章描述了生产场景，不意味着所有细节已公开。经验性建议与对照实验结果分别叙述。

## Agent 与评测场景示例

- 区分任务终态是否正确、过程是否合规、工具调用是否有效；仅输出流畅不代表完成业务。
- 识别环境状态、执行轨迹、评分器、人工复核和运行条件之间的关系。同一任务在工具故障或数据更新下可能产生不同结果。
- 查清评价对象是基础模型、Agent 系统、单个工具还是完整业务流程，避免直接横比不同对象的分数。
- 记录预算和反复尝试条件，尤其是 token、执行次数、时间与人工修正。用户项目不必复刻大厂规模，但需要可复现地证明自己的改动。

## 交付实践卡

每项建议包含：来源 `material_id/work_id`、可选目标 `job_key` 和要求原句、待解决问题、已核验代码模块、用户自己的改动、基线与验收、数据／资源条件、展示产物。

说明交付的是应用、工具还是组件，以及使用者的输入、关键处理和可核验输出。局部机制可以独立有价值，但不能将它的指标当作完整系统的成效；用户需要应用时，说明还需接通哪些环节、必要的真实调用和失败处理。推荐阶段没有执行，不应把这些必要环节从实施计划中删去。

先形成目标明确的最小实践候选，分别列核心范围和有条件的扩展；依据数据准备、代码改动、运行与人工核验估算工作量。完整项目卡与个人总预算按同套件的[项目规划](../_shared/references/projects.md)和[准备计划](../_shared/references/advice.md#准备计划与反馈)处理；独立调用本技能也可直接复用这两处方法，不要求启动其他子流程。

已核验代码按[目录格式](tracking.md)随材料传回 `code_checks`，不能只在采集者自己的分析文件里保存版本和路径。这样总入口可沿同一证据继续规划，避免重复获取或把候选链接当成已检查实现。

优先沿用用户已有业务或项目。没有画像时给条件化候选，例如已有工具执行框架的人可以做轨迹评价与恢复；有数据与模型实验基础的人可研究评分一致性。不要替用户编造业务经历。

把目标落到具体差异，例如“为失败恢复增加可复核的终态检查，并比较相同任务集的恢复效果”，避免只写“搭一个多 Agent 系统”。验收方案不能代替真实实验结果；报告作者的收益也不能移植成学生项目的预期数值。
