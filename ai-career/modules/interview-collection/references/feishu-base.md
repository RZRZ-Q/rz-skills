# 将整理结果写入飞书多维表格

用户明确要求飞书时，按本文维护原始面经与题目两表；派生题库按[岗位题库](role-question-bank.md)，复用本文的身份、选项和失败恢复规则。

## 目标与身份

工具、认证与首次目标选择按[首次引导](onboarding.md)，命令以本机 `--help` 为准；全程 `--as user`，不自动切换 bot。

- 本次明确给出的表格链接优先，用 `base +url-resolve --url "$BASE_URL" --as user` 取得真实坐标；链接不含表时用 `+table-list` 定位，多个候选不能猜。已有“面经”和题目表优先复用，先读取两表字段与关联目标。
- 本次未给新链接时，首次引导先让用户选择新建或追加；已有默认目标可作为追加选项说明，不能把“有配置”当作首次写入同意。用户要求独立测试或不沿用旧配置时不读取旧目标数据。已明确要求继续追加默认表的任务按下述配置核对，不重复问。用户明确要求新建时，先创建 Base 和“面经”首表，再在同一 Base 创建“面试问题”表与双向关联；不能因默认目标失效而自动建表。
- 每轮中间文件放在用户项目的独立 `tmp/` 子目录，先设置 `umask 077`；CLI 文件参数使用 cwd 下的相对路径。凭据不进入文件或 Skill，目标 token 不硬编码。

### 用户本地默认目标

配置默认位于 `~/.config/organize-interviews/feishu-target.json`；显式设置的环境变量 `ORGANIZE_INTERVIEWS_FEISHU_TARGET` 可覆盖该文件路径，供用户指定或隔离测试使用，不更改 `HOME` 或 Lark 配置。配置只保存：

```json
{
  "identity": {"brand":"feishu","app_id":"实际应用 ID","user_open_id":"实际用户 Open ID"},
  "base_url":"https://example.feishu.cn/base/实际目标",
  "post_table_id":"实际面经表 ID",
  "question_table_id":"实际题目表 ID"
}
```

运行 `lark-cli whoami --as user` 获取当前身份。它直接返回 JSON，不使用 `ok/data` 信封；从 `brand`、`appId`、`onBehalfOf.openId` 取得上述身份三元组，并确认 `identity=user`、`available=true`。不按昵称识别账号。

复用默认目标前比较身份三元组，并读取目标、字段与双向关联核对权限和归属。账号不同、配置不全或目标不可访问时报告阻塞，不换账号、覆盖绑定或创建替代表；配置不替代本次写入意图。

只有用户明确要求“后续复用／设为默认”，且已授权向该目标写入、目标已真实读取验证后，才保存或替换配置。本次临时提供另一个 URL 不自动覆盖默认。写配置前设置 `umask 077`，配置文件 `0600`、专属目录 `0700`；即使不含密钥也不提交 Git，隔离配置同样放在忽略目录。不存正文、令牌或授权码，不向用户展示完整身份或配置作为交付。

## 采集前读取已有链接

追加已有表时，在访问来源平台前完成上述身份与目标核对，用 `+record-list` 读取主表全部“来源链接”，只投影这一列即可，不提前读取全部题干。以 NDJSON 导出结果为准，检查 `records_count`、`has_more`；未读齐时沿返回的分页继续，不用筛选视图代替全表。不完整或失败的读取不能当作空库；若被外层调度限制飞书访问，应先等待读取时段，不先采集一批再补排重。本机 `--help` 不访问飞书，可提前查看；并行采集可复用宿主本轮为同一目标取得的完整链接快照，写入仍需串行复查。

按 [采集子流程](find-interviews.md) 的规范链接和本轮读取集合规则排除重复候选，命中就跳过详情和读图。一个合集链接可对应多条主记录，但读取时仍只算一个来源。明确新建空表时初始集合为空；普通检索／Markdown 输出不读取飞书。

这一步只优化链接访问。普通追加不重读旧帖、也不自动补旧帖的未读图片。用户明确要求补齐、重读，或继续一次已知未完成的导入时，先复用已保存材料与返回的 record ID，仅按授权范围读取缺失部分。已有旧式整帖合集不在普通追加中自动拆分或另建一套。

## 一篇面经与它的题目

“面经”表一篇一行，“面试问题”表一题一行；通过双向关联，在一篇面经的“面试题列表”中逐条查看、打开题目。不要把所有 Q 拼成一个可编辑长文本字段，也不用多选标签代替题目记录。

分篇及题目归属按[整理子流程](organize-interviews.md)。合集主记录标题用“原帖标题｜原文篇章称呼”，无篇章标题时用公司／岗位加图号或段落定位；题目的“来源标题”仍用原标题，“原文位置”指向实际篇章。归属待确认的摘录留在本地，不另加场次表。

### 面经表

| 字段 | 类型 | 内容 |
|---|---|---|
| 标题 | text，主字段 | 单篇用原标题；合集拆篇保留原标题及明确篇章称呼／定位 |
| 平台 | select，multiple=false | “牛客”“小红书”“知乎”“B站”“无”，按已核实来源站点填写，与公司分开 |
| 公司 | select，multiple=true | 标准公司名，按公司归一规则匹配；单篇通常一个，兼容旧合集的多个公司，缺失选“未知” |
| 岗位 | select，multiple=true | 根据原称和明示职责归一的岗位；单篇通常一个，缺失选“未知”，招聘阶段放招聘类型 |
| 公司原文、岗位原文 | text | 保留本份经历的原始称呼，包括外号、emoji、岗位修饰；不以标准选项覆盖原称 |
| 部门 | text | 本份经历原文明示部门、团队或业务线，无法辨认填“无” |
| 招聘类型 | select，multiple=true | 只汇总本份经历已确认的类型；共同信息按整理规则判断，不从泛化标签或其他篇章推断 |
| 轮次 | select，multiple=true | 按原文汇总本篇轮次，未说明时选“未知” |
| 面试日期 | text | 按已知精度填 `YYYY-MM-DD`、`YYYY-MM` 或 `YYYY`；多轮日期可列明或写“多轮，见题目”，缺失按整理子流程的日期规则处理 |
| 来源链接 | text | 规范公开链接；本地材料留空，不上传本机绝对路径 |
| 面试题列表 | link | 双向关联“面试问题”表，反向字段名“所属面经” |

准备建议、待确认内容和候选人反问放在主表现有说明列；确有需要且无合适列时加文本“补充说明”，不计入实际题目。日期提取统一按[整理子流程](organize-interviews.md#提取面试信息)。

转载／汇编、篇章关系待确认或局部未读影响使用时，也在此说明列写明，例如“转载合集中的某篇；实际面试日期未明”或“已读第 5–6 图；本篇二面后半未读”。写在对应主记录，不能只留本地日志；已完整读取的其他篇章不标成未完成。全帖仍有未读篇章时在交付中说明，不为空篇建记录。缺列仅在实际需要这些说明时增加一列 text；不增加专门状态系统。用发帖年补面试日期只表达已知精度，不证明转载内容是近期面试。

### 面试问题表

| 字段 | 类型 | 内容 |
|---|---|---|
| 原文问题 | text，主字段 | 原句及连续追问，保留原有“Q：”、标点和空白，不扩写或补答案 |
| 题号 | number，整数 | 每条主记录内按原文顺序从 1 递增，同一经历的多轮不重置；用于排序，不冒充原文编号 |
| 平台 | select，multiple=false | 与本题所属来源篇一致，取“牛客”“小红书”“知乎”“B站”“无” |
| 公司、岗位 | select，multiple=false | 本题所属经历的标准公司和岗位；每列单元素数组，不套主表合集的全部选项 |
| 公司原文、岗位原文 | text | 本题所属经历的原始称呼，保留归一前依据 |
| 部门、面试日期 | text | 本题所属场次的信息，不能直接套用主表的多轮概览；部门无法辨认填“无” |
| 招聘类型 | select，multiple=false | 只填本场的一个类型，不能套用主表汇总；大类不细分时选“未注明”，完全不明选“无” |
| 轮次 | select，multiple=true | 只填本题明确所属轮次，不套用主表全部选项；未说明时选“未知” |
| 来源标题、来源链接 | text | 原材料标题及公开链接；本地链接留空 |
| 原文位置 | text | 实际核对过的轮次／篇章／行号；图片写已确认的原帖图号，未知时写本地图片编号，再加图内题号／原句，不把下载顺序当原图序；同题有图文双出处时并列保留，不上传本机路径 |
| 所属面经 | link | 由双向关联自动创建；每题只关联它所属的一篇面经 |

不同链接和不同经历的相同问题分别保留，不做跨链接内容相似或转载同源去重。原文有独立编号的两条提问即使重复，也各保留一条。题号是导航和排序，不能替代原句与来源位置；关联字段只保证集合，不能依赖其返回顺序表示题序。

### 公司与岗位选项

公司／岗位按[归一规则](company-role.md)复用或追加规范选项，两表名称一致；创建时使用该文的公司预置表与实际岗位。更新选项前读取完整字段定义，保留旧选项和配置，仅追加所需项，再写记录。所有 select 的 CellValue 均用选项名数组，单选也不写字符串。

字段读取／更新响应的 `options` 可能只含前 50 项，并带 `truncated`、`remaining_options_count`。不能用截断列表覆盖字段；此时先用 `+field-search-options --limit 200` 读全，按 `total`、已读数量及 `offset` 续页，再合成完整选项列表。回读预置公司数量也用完整列表，不能把响应前 50 项误认成全部选项。

原文列保存实际称呼；没有依据时留空，标准字段选“未知”。旧数据迁移与原称保留按[归一规则](company-role.md#旧合集和原文)，不改标题、题干、部门和招聘类型。

用户明确要求将旧文本列改为选项时，先完整备份两表字段定义、公司／岗位原值和记录关联，再原地转换，保留原字段 ID。转换用的临时选项必须覆盖所有旧非空文本（包括旧合集的复合字符串），避免不匹配值丢失；随后逐记录写标准选项并保留原值，读回数量、值和关联后，才去掉本次迁移产生且已不再使用的别名／复合临时选项。旧合集主表分别汇总选项，题表仍按每题已有归属；不在这一步拆篇或重分配问题。已有原文字段或人工值不得覆盖；发现与备份不一致时先核查。

平台、招聘类型、轮次的取值语义见整理子流程，单／多选依上方字段表。例如平台 `["小红书"]`、招聘类型 `["实习（未注明）"]`、轮次 `["一面","二面"]`；未知轮次 `["未知"]`。平台按规范来源链接识别，无法确认填 `["无"]`；仅为本轮实际需要的平台补缺失选项，不顺带迁移旧记录。

轮次不是封闭词表，原文有其他已完成轮次时保留称呼并补选项，同义写法复用；备注不拼入轮次选项。已完成但未披露问题的轮次可汇总主表，不能生成题目；仅预约轮次不计入。

## 建表与迁移

按上方“面经表”的顺序生成完整字段对象数组 `post-fields.json`，合并列名分别建字段，标题置首，暂不建关联字段。文本字段用 `{"name":"字段名","type":"text"}`；选项字段用 `type:"select"`、表中指定的 `multiple` 和 `options:[{"name":"选项名"}]`。公司预置和岗位按归一规则补齐，均含“未知”选项；招聘类型取整理流程的完整列表。

轮次常用初始选项为“一面、二面、三面、四面、五面、技术面、HR面、终面、笔试、未知”，另补原文明示的轮次。保存 JSON 后一次创建 Base 和首表：

```bash
lark-cli base +base-create --name "面经整理" --table-name "面经" \
  --fields "$(cat ./tmp/本轮目录/post-fields.json)" --as user
```

先判断响应 `ok=true` 与 `data.created=true`，再从同一对象读取 `data.base.base_token`、`data.table.id`、`data.base.url`。表 ID 是 `id`，不是 `table_id`；不要把成功判断得到的布尔值当响应对象。坐标为空时停止，不发送空坐标请求，也不重复建表。

在同一 Base 用 `+table-create --name "面试问题" --fields ...` 创建题表；第一个字段为“原文问题”，其余按上表建立，其中“平台”沿用上述单选配置，“公司、岗位、招聘类型”沿用主表完整 `options` 并将 `multiple` 设为 `false`；“轮次”沿用上述多选配置。先不手动建“所属面经”，然后在主表创建一次双向关联：

```json
{"name":"面试题列表","type":"link","link_table":"实际题表ID","bidirectional":true,"bidirectional_link_field_name":"所属面经"}
```

```bash
lark-cli base +field-create --base-token "$BASE_TOKEN" --table-id "$POST_TABLE_ID" \
  --json @./tmp/本轮目录/post-link.json --as user
```

用返回字段 ID 和 `bidirectional_link_field_id` 核对两端关联的表。不要再手动创建第二套反向字段。

已有表按字段含义复用，补必要缺列，不随意改名或类型。普通追加不顺带迁移旧数据；用户明确要求迁移时，先备份受影响的两表字段、原值、record ID 与关联，只改指定字段，保留原句、人工值及其他内容，回读核对后完成。

- **长文本改题目列表**：`text` 不能原地转 `link`，需新建关联字段。原句、来源与位置一致的逐题记录复用 ID，只补题号和归属；不同归属报冲突。核对后可将旧长文本从默认视图隐藏并保留备份，不维护双份题干。
- **补平台**：只在缺列时创建单选字段，按规范来源链接回填空值；题目缺链接且唯一归属已核对时可继承面经平台，否则填“无”。已有非空值冲突不覆盖；每次仅更新“平台”，必要时将新列加入原视图，保留其余配置。
- **补部门／招聘类型**：按已核实来源映射原 ID，只补这两列和确需拆出招聘阶段的岗位。部门未知填“无”，岗位／类型拆分按整理规则。
- **轮次转多选**：全量备份轮次原值与配置，按原文拆分并补齐选项，以原字段 ID 转为 `select`、`multiple=true` 后写数组。题目只填自身轮次，无法确定填 `["未知"]`；不建替代列、不把多轮原值当一个选项。
- **补面试年份**：按整理日期规则，只更新受影响的主记录及对应场次题目日期，保留原文明示精度。

主表默认视图把“面试题列表”放在标题旁；题表按数值题号升序。修改视图前读取原配置，只调整本次需要的列或排序，不删除其他视图。展示效果须实际打开关联列表核对，不能仅凭 API 成功声称已呈现。

## 写入与排重

1. 逐篇完成写前原文审读后准备元数据和有序题目，不靠固定 Markdown 样式的通用正则重新抽题。进入串行写入时段后重新读取主表全部记录的必要元数据、来源链接、说明及关联列；不能拿采集前链接快照替代当前状态。普通全新来源追加不读取全量题干；补齐或迁移时按下文读取相关题目，写入结果不明的恢复仍须完整核查两表。重复传 `--field-id`，统一输出 `--format ndjson --output ./tmp/本轮目录/existing.ndjson`。NDJSON 导出 stdout 是 manifest，直接读 `records_count`、`has_more`，不套普通 JSON 的 `ok/data` 路径；普通 JSON 命令才使用 `ok/data`。
2. 读齐本次所需范围的记录后再排重：主表必须完整，定向题目读取也须覆盖相关主记录的全部题目。`has_more=true` 时沿返回的 `next_offset` 继续，分页 `rev` 与 `query_context` 须一致，变化就停止。不要用会隐藏记录的视图代替全表排重。文本缺失／`null` 只在比较时视为空字符串，其余字符不裁剪。
3. 先按规范来源链接复查：普通追加中新候选若已被其他运行写入，就跳过该来源的全部待建记录，不能据旧快照重复创建。一个尚不存在的合集来源可按本轮明确篇章一次创建多条主记录，不能在本批创建第一篇后把其余篇章当作重复链接丢掉。明确补齐或恢复时，按“规范来源链接＋原文经历篇章”对应已有主记录：可复用主表标题中的篇章定位和题目的原文位置，不凭当前数组序号或公司＋岗位猜对应。相同链接的不同篇章合法，同一篇章有多条记录或无法唯一定位才报冲突。无公开链接时用已明确区分的材料名／篇章。旧式整帖记录保留原样，不自动拆分、改号或追加一组新拆篇。
4. 明确补齐或迁移时，按已对应主记录的 ID 和关联范围读取相关题目字段，不必导出无关题干；即使主记录已存在也不能略过未完成题表。写入结果不明的恢复按下文先全量读取两表，再定位相关题目。按“所属面经 + 题号”定位并核对原句和位置；来源位置仅措辞不同且可核实时复用旧写法。补读使题目插入原有序列中间、从而需要改已有题号时，先报告需要重排，不自动把错位题目当新题追加；普通补齐不修改旧题号。原句、真实位置或场次冲突时报差异，不覆盖。旧表尚无关联时，读取明确迁移范围内的候选题目，仅复用可唯一对应的记录，不能把无关联当作没有旧题。
5. 新篇先用 `+record-batch-create` 建主记录，按成功返回取得真实 ID；新题使用 `{"create_records":[{"原文问题":"原句","题号":1,"所属面经":[{"id":"实际主记录ID"}],"其他字段":"对应值"}]}` 写入题表。双向关联会自动更新主表列表，不另写一次主表关系。每批最多 200 条，同表串行执行；没有新增就不发空写入。
6. 已授权迁移用 `+record-batch-update` 按上述范围更新核实过的 record ID；关联值为 `[{"id":"实际记录ID"}]`。普通追加只增加缺失记录，不自动改写或删除旧题与人工内容。

普通 JSON 成功按退出码 0 和 `ok=true` 判断；成功 JSON 来自 stdout，失败 JSON 来自 stderr，不解析失败命令的空 stdout。核对返回 ID、数量与 `ignored_fields`，不能把两表写入当成原子事务。

### 只读 EOF 重试与断连恢复

以下规则适用于飞书身份／目标检查、采集前排重、写前复查和写后核验中的只读请求，不扩展到来源平台访问。

- 只有已确认是只读操作，且原始错误明确为 `network/transport` 的 `EOF` 或 `unexpected EOF` 时，默认有限重试：首次失败后等待 **5 秒**，再次发生同类错误后等待 **15 秒**，最多 **2 次重试（含首次共 3 次）**。成功就继续当前阶段；用尽次数或剩余执行预算不足时停止，报告已完成数量、原始错误和未完成范围，不要求用户为范围内的重试再次批准。
- 重试沿用同一身份、目标、筛选和字段范围，使用新的本地日志／导出路径，保留每次 stdout、stderr 和退出码；每次独立调用，不覆盖原失败，也不让后续成功命令掩盖失败退出码。失败导出的不完整 NDJSON 不能用于排重；分页中断时从头重新完成本次所需范围的读取，不拼接前次残片、不混用分页版本。重启读取也计入上述重试上限，不能按页重置预算。
- 认证、权限、限流、验证码、访问限制、参数错误或其他网络错误不套用该 EOF 重试；后续尝试遇到不同错误即停止。不能仅凭非零退出码重试，不自动换账号、代理或重新授权。

- 写入已成功返回记录 ID，仅后续只读请求出现 `network/transport EOF` 时，标记“写入成功，核验待完成”，保留成功响应、本地材料和失败输出。恢复时沿用已核实的身份与目标，只续做飞书核验，不重新采集或重发创建请求。跨会话恢复先重新核对身份与目标。
- 写入命令报错、部分成功或结果不明时，保留现场并停止后续写入，不盲目重发；不能把断连当作“未写入”。恢复后先全量读取两表，用已返回的 record ID 或“规范来源链接＋原文经历篇章”定位主记录，再核对该记录内的题号及实际落地情况，只补缺失项。
- 创建、更新、迁移字段、记录或关联等写操作均不适用上述自动重试。恢复只读同样受 EOF 次数与预算限制；远端实际落地情况尚未读清时，不能继续写入。需要全表比较时，按 ID 的局部回读不能替代它。

## 验证与交付

本轮写入完成后按返回 ID 回读新增／迁移记录及其主记录：核对主记录及题目数量、全部原句和位置、题号、所属场次元数据和题目反向归属。普通追加的新篇，其主表关联集合应恰好对应本篇全部新增题目；补齐时应对应已核实旧题与本轮新增题目的并集，不能把保留的旧题误判为多余关联；迁移时也须计入本篇复用的旧题。平台、招聘类型与轮次按选项名集合比较，两表平台与题目招聘类型单选恰有一个值，平台与来源一致；关联 ID 按集合比较，展示排序按数值题号验证。异步暂未可见时说明待确认，不重复创建。

相同输入再次核对，两表均应新增 0。最终返回主表真实链接，分别报告新读来源帖子数、跳过的重复链接数、新增面经记录数和题目数；一个合集拆出的多篇不能算多个来源访问。明确补齐时另报已存在、补齐、冲突和未写入数量，补齐题计入新增题数、不重复计数。只生成 JSON 或 dry-run 通过只能称为待写入；不要把中间 JSON 或本地配置交给用户操作。

## 入库后的图片清理

原文复核、两表写入和回读全部完成后，直接删除本批采集的原图、截图、裁剪图及重复副本，不转存备份或废纸篓；安排了退出后宿主审查则等其完成。用户要求保留的图片、用户原始文件、fixture、正式附件及未完成批次所需图片不删除。

保留来源链接、标题、原句、图内位置和入库结果，说明清理数量与字节数；本地图片编号只表示当时核对的位置。后续复审从来源链接重新打开，不为清理而重新联网或重复入库。
