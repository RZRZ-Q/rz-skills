# 综合岗位、工程与研究证据设计项目

## 先定需要证明的工作能力

从具体 JD 原句或用户真实的业务／研究目标挑出最值得补的一项能力，再结合 `ai-tech-radar` 的案例、论文与已核验代码选择实践。缺少 JD 不妨碍做成长项目。不要从热门仓库榜反推用户该做什么。优先复用用户现有项目；有合适基础时做实质改进比另开同类项目更合适。

按[前置能力诊断](advice.md#前置能力诊断)检查当前最小交付真正依赖的能力，用已有证据决定哪些可直接开始、哪些先补或边做边补；只对会改变方案的未知项补证据。

每次深入少量最相关候选：查看官方仓库 README、实际代码／示例入口、许可证、最近可见维护情况、运行环境与模型／硬件要求。保存仓库 URL、检查日期和所查 commit 或文件路径。引用项目实际支持的能力，缺少核验只列为待查候选。近期没有提交本身不等于项目不可用。

先确定交付的是业务应用、评测工具还是基础组件，以及谁使用、输入什么、得到什么结果。三者都可成为合适项目，但边界应匹配用户目标：应用项目要覆盖核心处理／调用、结果交付及失败处理，组件或评分工具要说明独立用途和上下游依赖。不能用检索指标代替回答质量，或把日志分析说成已经完成业务任务。

推荐阶段尚未执行模型或工具，不意味着计划只能停在离线练习。用户需要完整应用时，将必要的真实调用和端到端验收纳入后续实施范围；离线阶段用于打基础或降低调试成本。若资源只够组件项目，明确它能证明的能力及补齐应用还需要什么，再决定是否作为主推。

## 把推荐落成项目卡

| 项目卡字段 | 必须能回答的问题 |
|---|---|
| 对应目标 | 哪个岗位原句或用户目标、哪种能力深度？ |
| 交付边界 | 应用、工具或组件？用户路径和输入／输出是什么，哪些依赖还未具备？ |
| 方法依据 | 哪个工程案例或研究工作、哪些证据支持采用这个方法？保留 material_id/work_id |
| 代码入口 | 在哪个仓库、模块或示例中实施？ |
| 用户自己的工作 | 要增加／修复／比较什么？仅安装或跑通 demo 不等于原创贡献 |
| 最小可验收结果 | 什么真实任务、数据、指标与基线能说明改动有效？组件指标与最终交付是否分别验收？ |
| 展示证据 | 可复现命令、关键代码、结果与失败分析、演示或贡献记录；哪些产物支持下方的能力与面试主张？ |
| 时间与资源 | 最小完整版本的任务估时能否放入总预算和各期容量，并支持对应里程碑？按[准备计划](advice.md#准备计划与反馈)从同一份估时排期；未实测值标估计，扩展另列条件 |

如果 `ai-tech-radar` 已在本轮核验过仓库入口和版本，直接复用；只有代码、目标或来源发生变化才重新检查。通过[衔接说明](handoffs.md)保留材料／代码链接，需要岗位映射时再关联 JD，最终解释用户自己的工作，不堆叠阅读列表。

同一方向可按当前水平给出递进范围：理解并复现 → 做明确改动并评测 → 解决真实问题或贡献上游。只展开用户当前需要的一档，不要求每人走完所有阶段。设计评测应服务于项目主张，不自动扩张成论文级实验。

先推荐能独立交付的最小版本，再列有额外时间或结果支持时的扩展。对照使用当前目标下有意义的现成方案，在相同任务与资源条件下比较；计划验收目标、作者已报告的结果与学生实际测得的结果分别记录。最终按用户需求检查完整路径，不以所有卡片字段都填满代替可行性判断。

示例任务形态（是设计方向，不是固定项目推荐）：

- 评测／数据：引入一类真实任务，定义可复核标准，分析评测误差与数据质量对结果的影响。
- Agent 应用／Harness：接入真实工具，整理失败任务，改进执行或恢复机制，用同一任务集比较完成情况。
- 后训练／Reward：实现一类奖励或数据策略，检查奖励是否与任务成功一致；在预算允许的规模验证训练收益。
- 训练／推理 Infra：定位明确瓶颈，在固定负载与硬件条件下比较吞吐、延迟、显存或稳定性。
- 领域 AI：把用户熟悉的业务工具接入任务闭环，用领域指标评估效果。

## 项目成果与面试主张

规划时列出拟证明的能力与所需证据；有真实产物后，再形成可用于简历或面试的表述。同一项目沿用 `project_id`，每项独立主张保留稳定 `claim_id`，供[进展续接](progress.md)及[面试衔接](handoffs.md)引用。未验收的内容保留为计划，不提前转成成果。

| 主张记录 | 必须能回答的问题 |
|---|---|
| 标识与目标 | `project_id`、`claim_id` 对应哪项用户目标／能力？需要岗位关联时保留 JD 原句或 `job_key` |
| 个人贡献 | 哪些由用户实现、修改或分析，哪些来自上游、协作者或工具？依据是什么？ |
| 产物与版本 | 仓库、commit/ref、文件路径、运行记录／演示／结果文件在哪里？本次证据对应哪个版本？ |
| 条件与核验范围 | 使用什么任务、数据、环境、比较方案与指标？实际检查／执行了哪些部分，结果是什么？ |
| 支持的表述 | 这些证据允许用户具体声称做过什么、得到什么结果？若尚不足，标为待补证据 |
| 未覆盖与下一步 | 哪些规模、场景、解释或独立修改能力尚未验证？补哪项产物或验收能支持下一层主张？ |

代码存在、实际运行成功、测得指标和能够解释／修改分别记录，不能互相代替。计划目标、论文作者的结果与用户实测结果保持分离；沿用开源实现时可描述复现、集成或实测贡献，但不把上游功能写成自己的原创实现。一次小规模实验按其条件表述，不升级为未经历的生产或大规模经验。

同一版本的已有核验证据直接复用。版本、目标或结果改变后，只重新检查依赖这些变化的主张；旧结果仍属于原版本，不能直接覆盖未测的新版本，原记录通过进展报告保留。

面试准备围绕这些主张组织问题、设计取舍、失败分析和个人贡献的讲述；自行拟定的追问标为练习题。实际公司原题、题库与刷题流程仍交给 `interview-collection`，没有该技能也可完成项目成果梳理。

推荐或设计不自动执行训练、付费 API 调用、上游提交或投递。实际实施按用户本轮授权推进，使用真实命令和结果验证；不要创建假结果来让项目卡看起来完整。
