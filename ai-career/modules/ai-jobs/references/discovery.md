# 岗位发现与 JD 提取

## 先确定能影响结果的范围

沿用对话已有的公司、地区、阶段、方向和时间范围。仅当缺失条件会实质影响结果时集中询问。没有限定的探索请求可以先用中国大陆公开 AI 技术岗位，按实习／校招／社招与公司规模分层做小批次调查，明确这是默认范围。采集数量与停止条件按本轮范围、用户数量要求及可用预算确定，已有工作清单配置可复用。

“覆盖大中小厂”要落实为来源覆盖，而不是把一家公司的岗位拆成不同组。先记一张本轮覆盖表：公司／规模分组依据／官方招聘入口／招聘阶段／目标方向／成功读取数／未覆盖原因。未找到可信的中小公司资料时保留空缺。

调查“当前／近期需求”时，先沿用或明确本轮时间窗口，分别记录近期发布／更新的 JD 和本轮确认在招的 JD：发布日期未知的岗位仍可能在招，近期发布的正文也未必仍可投递。覆盖表分别计完整正文数、当前在招数、窗口内发布／更新数，并保存日期依据；不以读取日期、阅读器响应头或搜索收录时间替代岗位日期。

跨公司调查按所选公司／阶段检查缺口，给近期候选的发现和状态核验留出预算。达到正文数量后，若当前在招样本仍只集中在少数来源，优先补范围内尚缺的公司／阶段，不继续用易读旧材料凑量。停止时说明哪些范围已获当前证据、哪些仅有正文或未完成核验，不把公司配额或关键词选择造成的分布当成市场集中度。

需要找公司入口时，先读取[存储助手](../_shared/references/storage.md)返回的岗位 watchlist；首次使用可从[官方入口清单](source-list.md)选择符合本轮范围的来源。清单是起点，不是完整市场；新增公司与关键词按[清单维护](tracking.md#来源清单与扩充)处理。校园届别从当前官方项目核实，不沿用固定清单编写时的年份。

## 搜索和确认

1. 给定材料优先读取材料；给定链接优先读取链接。需要搜索时，组合公司招聘入口、具体业务能力词、招聘阶段、城市／届别。可用查询形态：`公司名 招聘 方向 实习`、`公司名 校园招聘 2027 算法`、`方向 城市 社招 招聘`。年份来自用户和当前招聘批次，不固定写死。
2. 优先公司官方招聘站、官方招聘账号和可确认归属的招聘系统。聚合站、社区内推、搜索摘要用于发现线索；读到正文前不把摘要当完整 JD。中小公司的官方发布可能在其自有网站、招聘平台认证主体或官方账号，保留来源类型与实际证据。
3. 用现有搜索／网页读取能力；动态页面可用已授权浏览器。登录、验证码、访问限制导致无法读取时，记录未覆盖，继续独立来源。不要猜私有接口、自动登录或把失败变成“岗位已下架”。
4. 记录详情页中的标题、招聘主体／部门、岗位 ID、地点、招聘渠道、届别、原始学历／经验字段、职责、要求、优先项、发布日期／更新时间／截止日期以及投递入口。来源没写的留空；薪资、级别、HC 不从标题、公司名或经验年数推算。
5. 仅在明确的在招标识、有效投递入口或其他来源可见证据支持时记 `open`；明确的停止招聘标识或官方终止声明支持 `closed`。历史材料及仅有正文但状态不清的页面记 `unknown`。保存状态证据与核验时间。

同一岗位的字段可能分布在列表、详情和招聘项目中。按岗位 ID 或已核实的链接关系合并已取得的证据，分别保留字段出处；详情未写不等于来源未提供，招聘渠道也不能代替届别或毕业日期资格。冲突信息并列说明，不用统一模板覆盖原值。

近期检索先检查官方现行招聘目录、当前招聘批次及其实际提供的日期／排序，再打开详情；站点没有排序能力就保留该限制。搜索为空、只返回旧条目或正文空壳时，在本轮预算内沿官网当前招聘外链、团队招聘入口、已发现的准确职位名或另一可用读取方式补查，并保存尝试结果。只有目录标题／摘要、未取得完整职责与要求时不能计为完整 JD；目录本身提供完整正文时注明实际出处。来源受阻与尚未检查分别记录，不自动换成更多旧样本。固定公司任务不借补查扩到范围外公司。

交付时从各路径的实际结果汇总“正文是否取得”“在招依据是什么”“申请入口是否确认”。直接请求失败与阅读器／浏览器正文成功可同时成立；不要以某一次失败覆盖同岗位已取得的字段，也不把正文成功升级为申请链路可用。状态结论连同依据和限制传给后续匹配。

## 从文本提取能力

按以下顺序整理同一份观察 JSONL，不先凭“核心／重要”给条款赋 `must`。

1. **原句与作用范围**：保存完整 `raw_text`，逐条保留原句、`source_ref`、所属 `section`，有相邻限定时保存 `qualification_context`。原文按来源分存；合并保存时，定位同时包含来源标识和该来源内的位置，不能只用重复的网页行号。标题范围延续到下一处同级分区，换行不结束范围；局部优先、任选和放宽说明优先于外层标题。要求与加分并存时按分句修饰范围拆分，保留“或”“至少一项”“可放宽”等逻辑；不能安全拆分时保持原句。团队介绍、福利、投递说明和导航留在原文，不混进条件；重复渲染只提取一次。
2. **来源强度依据**：候选条件先写 `strength_basis`，包括 `level`、直接引自 `raw_text` 的 `quote` 和该引文的 `source_ref`。引用应能说明本条强度，可来自条款或确实管辖它的分区标题；结合局部限定判断，不能仅凭所在位置、内容重要性或后面另有加分分区推断必需。`required` 表示来源明确作为必需要求，`preferred` 表示优先／加分，`soft` 表示适配特征或非强制期待，`unclear` 表示强度或修饰范围不明确。职责直接标 `responsibility`，不套候选资格的强度。结构化学历与正文门槛冲突时保留两者，不选择较严格的一项代替事实。
3. **生成分类并复核**：运行[准备命令](tracking.md#标准库账本命令)将草稿整理成待入库 JSONL；`required → must`，`preferred → preferred`，`soft/unclear → unspecified`，职责保持不变。`must` 只表达来源必需，不兼任核心能力或匹配重要度；缺乏可确认强度的候选条件保留为 `unspecified`。对照命令输出中的原句、依据、分区与限定，核实每项强度的语义及覆盖范围；备注不能豁免分类冲突。发现错误修正草稿并重新准备，再将复核后的同一份输出用于统计和入库。脚本校验引用存在及分类映射，不判断引用是否足以支持该语义。

同时保存任务、技术方法、工具和能力深度，“参与”不自动等于“独立负责”。技术标签用于检索与统计，保留原称及必要归一化；共享工具的技术方向不自动合并。岗位匹配区分职责、必需、优先与未明确强度，并读取原始逻辑；内容的重要程度由分析解释，不改写来源强度。

使用[记录格式](tracking.md)入库。一个岗位同时支持多个职业方向，但只有一个稳定身份。同名跨团队岗位不能仅凭标题合并；只有链接的“近邻岗位”放入待采集线索，不混入完整 JD 样本。

招聘系统常用 hash 路由区分列表与详情。向 Jina 等读取器传入已观察到的 URL 时，确认内嵌 `#` 没有被 HTTP 客户端当作本地 fragment 丢弃；必要时仅在读取器请求中编码为 `%23`，保存的官方 `source_url` 仍保留原始路由。响应只是首页时不能标记详情读取成功。官网已迁移招聘系统时，优先官网当前外链，旧搜索结果保留为历史／候选而非当前官方入口。
