# 按岗位生成或更新复习题库

生成或更新题库由用户选择；收尾提示与免重复询问条件遵循 [整理收尾规则](organize-interviews.md)。原始“面经”和“面试问题”继续完整保留；只在派生的岗位题库中归类、合并同义问法，不改原题、岗位、元数据或原表关联。在同一 Base 中按已确认的岗位类别维护题库，每行一个可独立复习的问题；原岗位名称用“来源岗位”字段保留，不为每个细分岗位或别名新建表。

## 岗位类别与已有题库

先读取目标 Base 的已有表、字段和类别映射，复用已核实的 table ID。若目标已有用户确认的分类，沿用该分类；没有时采用下列默认映射，并将本轮采用的“原岗位 → 题库类别 → table ID”留在工作材料中，供续批复用。表名用“类别名题库”，不因新增原岗位选项或同义写法再次建库。标记为“已合并”或归档的旧库只用于历史追溯，续批写入其已核实的目标库，不再向旧库追加或将其计入在用题库统计。

| 题库类别 | 对应原岗位与边界 |
|---|---|
| Agent算法 | Agent算法，独立保留，不与应用开发合成一个泛 Agent 库 |
| Agent应用开发 | Agent开发、Agent应用、Agent应用开发、Agent工具开发、Agent后端开发、Agent全栈；用“来源岗位”保留区别 |
| Agent评测 | Agent评测，独立保留；不把明确的测试开发职责仅凭“Agent”一词并入 |
| 大模型算法 | 大模型算法、大模型应用算法；原岗位仍分别保留 |
| 机器学习与数据挖掘算法 | 机器学习算法、机器学习与数据挖掘算法 |
| 世界模型与世界动作模型 | 世界模型（World Model／WM）、世界动作模型（World Action Model／WAM），以及明确包含该职责的基础与世界模型、端到端与世界模型；原岗位仍分别保留 |
| 具身智能与机器人算法 | 明确的具身智能算法、机器人大模型算法、机器人算法、VLA 岗位；仅题目涉及机器人或 VLA 不据此改归属 |

- 搜索算法、推荐算法、广告算法继续分别建库；AI后端开发与AI应用开发也分别保留。多模态、NLP、视觉、SLAM、AI Infra、风控等明确专业方向不为减少表数而强合。
- 泛称“Agent”的材料可依据同一场面试的完整原题、项目上下文及来源职责选择**派生复习类别**，不等于认定或改写实际岗位，“来源岗位”仍保留 Agent。例如整场围绕多任务训练、DPO／GRPO、蒸馏展开，可归 Agent算法；整场围绕应用架构、工具集成和工程实现展开，可归 Agent应用开发。不能默认归入工程类，不能靠单个训练或 RAG 关键词归类，也不为归类拆散连续的项目追问；用“归类说明”简记实际依据及其仅为复习分类。
- 宽泛岗位的材料若只有一道通用编程题、缺少整场上下文，可放入已有通用算法库的“Agent待归类”等视图，保留来源岗位并注明归类未定，不能据此认定为 Agent算法。没有适用的已有库时保留本地待分类清单，不为模糊称呼另建泛 Agent 表；其他归属不明材料同样保留并说明。
- 内容理解、多模态搜索、推荐搜索、人工智能研究工程等交叉或宽泛岗位，先核对实际范围及现有类别，再决定归属；映射不清时保留已有库，不凭名称、关键词或题量少强合。真实新专业方向确需单列时，说明它与已有类别的区别，按本轮已授权的建库范围执行。
- 同库内用“来源岗位”筛选细分岗位，用“主题分类”组织知识点；Agent应用开发可按实际题目设置架构、工具调用、记忆、RAG、后端工程等主题视图。视图复用已有名称与筛选条件，不用新表替代视图；同义主题统一选项，不将原岗位名混作知识点。

规整旧题库时，**迁移与语义去重分开**：先保存旧表／记录到目标表／记录的映射，完整迁移题干、变体、依据、原题与面经关联及用户字段；“来源岗位”从关联原题取值，不能由旧题库名反推。先回读验证覆盖和关联，再处理有明确题义依据的重复行；表数减少不等于题目去重。旧表仅在迁移完整核对后按用户授权收束，存在未迁移或归属不明记录时保留并报告。

### 题库侧栏分组

“世界模型与世界动作模型题库”和“具身智能与机器人算法题库”，以及后续已确认属于世界模型、世界动作模型或具身机器人方向的题库，统一放在根级 **“具身相关题库”** 目录，与“机器学习与视觉”等分组并列。组内保持独立题库，不合成一张泛具身表，也不因邻近技术主题移入视觉、机器学习或通用 Agent 分组。

新建或续更这些题库时，用 `+base-block-list` 核对目录和表的 `parent_id`，把目录 ID 一并记入本轮类别映射。复用已有“具身相关题库”目录；确有该方向题库需要归组且目录缺失时，用 `+base-block-create --type folder --name "具身相关题库"` 创建一次。新表或本轮范围内放错目录的旧表，用 `+base-block-move --block-id <实际表ID> --parent-id <实际目录ID>` 归组；均带实际 `--base-token` 和 `--as user`，不通过复制表或重建记录调整目录。完成后回读确认父目录与表 ID，保留题目、原题和来源关联；没有相关题库时不预建空目录。

## 选择范围与读取

- 用户只要求用现有表生成题库时，直接读取表内材料，不重新访问帖子、补读图片或搜索新面经。身份、目标、完整分页、私有临时目录和失败恢复沿用 [飞书写入说明](feishu-base.md)。
- 优先以“面试问题”每条记录自身的**岗位单选**取得原岗位，再按已确认映射选择题库。单选为空但“岗位原文”明确，且关联来源的标题／职责吻合时，可按[岗位归一规则](company-role.md#岗位)确定派生“来源岗位”，在工作材料保留依据，不回写原表；没有此类依据或信息冲突时保留待分类。不用“面经”合集中的多个岗位复制同一题到多张表，不凭题干谈到的技术猜岗位。不是已确认实际提问的材料不纳入，说明未处理范围。
- 读齐选定范围的原文问题、题号、公司、岗位、所属面经、来源标题、来源链接和原文位置；再读取实际关联的面经标题、来源链接和必要说明。保留真实 record ID。原题和主记录的来源不一致、缺少唯一所属面经时，先核查，不拼接出处或编造关联。
- 读取已有岗位题库的完整字段及全部行，再进行合并。用 `+table-list` 完整分页查找表；表名只用于定位候选，还要核对关联目标、字段含义及已有来源题的岗位。复用已核实的 table ID；同名多个候选、改名后无法确定原表或结构冲突时说明具体歧义，不另建一张相同题库。

## 按题义合并

逐题阅读，不以关键词相同、向量分数或固定正则代替语义判断。先理解各原题问了什么，再整理标准问题、主题和变体：

- 同一对象、同一核心要求且关键条件一致的问法可以合并。例如“解释 LoRA 原理”和“LoRA 如何实现低秩微调”可合为一题；“LoRA 的 rank 怎么选”仍是独立问题或明确的追问，不能因都出现 LoRA 而消失。
- 对比、原理、实现、调参、评估和场景设计不自动合并。同主题但答案范围不同的题分别保留；真正同义的问法才去重。标准问题是来源题义的清楚表达，不补答案、未出现的考点或技术限定。
- 标准问题直接呈现提问，不加入“某公司面经中的”“《帖子标题》中的”“该来源”“各来源分别对应的”或“项目／经历中的提问：”等出处说明。公司、平台、帖子标题和题号留在来源字段、“原题依据”或需逐来源说明的“变体与追问”中。例如“百度面经中的多 Agent 系统里，各智能体如何分工？”可写成“你的多 Agent 系统里，各智能体如何分工？”。公司名本身是提问对象或业务条件时仍须保留，不按公司名或“来源”等关键词一律删除。
- 标准问题只采用共同支持的范围，不能把某个来源的“原生／量化／上线后”等限定套给其他来源；条件不同但可作为同一问题的变体时逐来源注明，比较对象不同则分题。“是否使用”不能改成已经使用。拆题后补回原句中必要的场景与对象，使每行在筛选或排序后仍可独立理解，不留下“此类／这些”等跨行指代。
- 原题包含多个独立子问时，可以拆为多条派生题；每条都关联原题，在“原题依据”中标明支持片段和子问范围，例如“仅对应 PPO 损失函数子问；原句：……”。只在“变体与追问”或本地映射里写拆题说明不能替代该字段。不能将“原理、损失函数、实现、如何评估”等复合提问整组压成一个笼统的同类问题，也不能遗漏未覆盖的子问。
- 自我介绍等通用提问与实习、论文、项目追问出现在同一句时也须分别有去向；仅在整句引用中保留文字不算已整理该子问。
- 连续追问依赖前题时保留这种关系。具体场景、限制、数据规模、失败条件和不同问法放在“变体与追问”，逐项标明公司、来源标题和题号，不能剥去条件后假装完全相同。
- “介绍你的项目”“这个方案为什么这样做”等依赖个人经历的题，保留具体项目类型、技术条件和个人经历语境，用“你的项目／论文”等自然称呼，不用出处代替项目背景。未披露的背景在“原题依据”中注明；不把不同项目拼成同一个虚构项目，也不将来源未说明的项目推成通用知识题。
- 一条标准问题可以由多个来源共同支持，但每个原题只对其实际包含的部分作证。“原题依据”逐项写公司、来源标题、题号和支持的原句片段／子问；本地业务映射同时保留对应 record ID。不要让某公司因只问了其中一个追问而被表达成问过整组全部问题。

主题分类用少量能帮助复习的选项，如“大模型基础”“微调与对齐”“推理优化”“检索与 RAG”“项目与工程”；依据该岗位的实际题目确定，不为不存在的内容预设复杂层级。同义分类复用已有选项。

## 表结构与创建

| 字段 | 类型 | 内容 |
|---|---|---|
| 标准问题 | text，主字段 | 一个清楚、可独立复习的问题；标题不是稳定 ID |
| 主题分类 | select，multiple=false | 本题主要主题，方便分组筛选 |
| 变体与追问 | text | 有意义的问法差异、条件和追问，逐项注明来源标题与题号；没有则留空 |
| 来源公司 | select，multiple=true | 本行实际引用原题的标准公司集合，不套用主表合集全部公司 |
| 来源岗位 | select，multiple=true | 本行实际引用原题的已核实岗位集合，按上述单选／原文规则取值，不用题库类别覆盖细分岗位 |
| 归类说明 | text，可选 | 宽泛岗位的复习归属依据或待分类原因；与原岗位不同的复习归属须说明，普通明确岗位不必逐行填写 |
| 原始题目 | link，单向 | 指向原“面试问题”表，可关联多个真实 record ID |
| 来源面经 | link，单向 | 指向原“面经”表，取引用原题的所属面经 ID 并集，方便直达原帖 |
| 来源面经数 | number，整数 | 上述不同面经 record ID 的数量；同一篇多个原题只计一次 |
| 原题依据 | text | 逐原题列出公司、来源标题、题号及支持的原句片段／子问，保留拆题和合并依据 |

“来源面经数”是库内记录覆盖数，不代表独立作者、独立投递或真实面试频率；旧合集主记录仍按一个 record ID 计数。公司已知则采用原题标准公司，未知保留“未知”，不由帖子主题或主表其他公司补猜。

用环境已有 `lark-cli` 和 `lark-base` Skill；按本机帮助核对命令。字段配置沿用 `feishu-base.md` 的 CellValue 和选项完整读取规则。新建前准备实际主题／公司／来源岗位选项及两个真实来源表 ID，将以下结构保存为本轮 `bank-fields.json`：

```json
[
  {"name":"标准问题","type":"text"},
  {"name":"主题分类","type":"select","multiple":false,"options":[{"name":"实际主题"}]},
  {"name":"变体与追问","type":"text"},
  {"name":"来源公司","type":"select","multiple":true,"options":[{"name":"实际公司"}]},
  {"name":"来源岗位","type":"select","multiple":true,"options":[{"name":"实际原岗位"}]},
  {"name":"原始题目","type":"link","link_table":"实际题表ID","bidirectional":false},
  {"name":"来源面经","type":"link","link_table":"实际面经表ID","bidirectional":false},
  {"name":"来源面经数","type":"number","style":{"type":"plain","precision":0}},
  {"name":"原题依据","type":"text"}
]
```

只有本轮存在上述归类说明需求时，才在字段结构中追加 `{"name":"归类说明","type":"text"}`，已有同义字段按含义复用。

```bash
lark-cli base +table-create --base-token "$BASE_TOKEN" --name "已确认类别名题库" \
  --fields "$(cat ./tmp/本轮目录/bank-fields.json)" --as user
```

仅在本类别有可写入题目、已核对类别映射且没有可复用的现有题库时创建一次。读取成功响应中的真实表 ID 后继续，响应不明不能重发创建。两个 `link` 均设 `bidirectional=false`；不添加反向字段，不写来源两表。`link` 不传 `multiple`，多个关联用 `[{"id":"实际记录ID"}]`。已有题库按含义复用现有字段，缺少“来源岗位”时补列并按关联原题回填。公司／来源岗位／主题 CellValue 使用选项名数组；必要新选项先补齐，保留完整旧选项和配置。

## 写入与增量更新

1. 在本轮材料中保留候选行、每条原题的子问覆盖及对应的新增／更新判断，逐题核对上述合并条件。允许用简单本地工具计数和生成请求 JSON，不为题义判定增加固定脚本或 hash 标识。
2. 写前重新读取当前岗位题库，按**现有 record ID、题义、完整来源及原题依据**匹配。关联字段提供真实来源 ID，再按实际原句与题号核对可见依据，不能只靠标题识别。一条原题 ID 已出现在某行中，不表示它所有子问都已覆盖；每个子问仍须对应到正确派生题。标准问题改过措辞不应重复创建。多个旧行都可能匹配且无法明确处理时保留旧行，报告冲突，不自动删除或另建重复行。
3. 已有相同题义时复用其 record ID，补充缺失原题、来源面经、公司、来源岗位、变体和依据。更新后各集合取已确认旧来源与本轮新来源的并集，再计算不同面经数；不能用本轮范围覆盖历史来源。来源被更正时说明实际变化，核对受影响依据，不盲目覆盖用户手工改写的标准问题或清除旧来源。仅在确有独立新题义时新增一行。无变化的记录跳过，不发空写入。
4. 每条派生题的 `原始题目` 集合须与“原题依据”实际对应的来源集合完全一致；每项支持内容都能在关联原题的真实原句中找到。本地映射保留双方 ID 供核验，可见字段不堆放系统 ID。“来源面经”、公司和来源岗位从这些原题推得，不由标准问题概括或题库名反向猜来源。
5. 使用 `+record-batch-create --json @./tmp/本轮目录/create.json`，格式为 `{"create_records":[{"标准问题":"来源支持的问法","其他字段":"实际值"}]}`。已有行使用 `+record-batch-update --json @./tmp/本轮目录/update.json`，格式为 `{"update_records":{"实际题库记录ID":{"要变更的字段":"实际值"}}}`；均加实际 `--base-token`、`--table-id` 和 `--as user`。一批最多 200 条，同表串行。只写本次需要的派生字段，保留用户的其他字段、人工笔记和未处理记录。
6. 保留成功返回 ID、原始请求与响应；退出码、`ok`、`ignored_fields` 和失败处理遵循 `feishu-base.md`。结果不明时停止后续写入，完整回读岗位题库并对照本轮请求和来源映射，确认实际落地后才补缺失项；不能因标题不同或来源已关联就猜成功／失败。

复核发现本轮自己刚生成的题目有遗漏或不受来源支持的限定时，按已授权范围纠正派生行并回读，保留原始失败与纠正依据；不能将自己生成的错误当作受保护的人工内容而直接留在交付中。原先已有的人工改写仍按上述冲突规则处理。

## 核对与交付

写后回读全部新增／更新行，比较时沿用[飞书文本空值规则](feishu-base.md#写入与排重)，核对标准问题和变体、“原题依据”中的支持片段／子问范围、原题映射、两类关联集合、公司、来源岗位及不同面经数，并按需核对“归类说明”仍保留真实依据与不确定性；检查题干没有混入出处说明、必要场景与技术条件仍完整。再用同一输入和当前远端行重新判断，输入和远端均未变化时新增及更新应为 0，发生来源更正则报告变化。只生成本地 JSON 或 dry-run 不能算建表成功。

检查选定范围每个原题的完整提问是否已覆盖：一条原题可以对应多行，同一面经可以贡献多题。分别报告输入原题记录数、涉及面经记录数、派生题数，以及新增／更新／未变／冲突或未覆盖数量，不能把派生行减少数直接称为重复题数量。按原题依据检查语义覆盖，关联存在或行数相等不能代替它。

交付实际岗位题库链接和上述简短统计；说明主题与合并范围，保留未处理的具体原因。不声称本轮重审了未读取的原帖，来源表自身的缺失也不能被题库合并掩盖。

用户尚未选择下一步时，可提示“用这份题库生成知识点学习包和本地刷题页”；已有明确选择直接执行[学习包流程](study-pack.md)，复用本轮已核对的记录，不重复读帖或强制生成答案。
